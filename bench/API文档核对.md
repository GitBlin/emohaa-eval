# API 文档核对与 harness 判断

核对日期：2026-11-09。依据上一级 `智能体聊天最佳实践.docx`，并只读调用当前默认用户的机器人列表、全部15个机器人详情及最近会话历史。未发送新聊天消息，未清理上下文，未修改客户端或评测脚本。来源字段快照见 `api_document_audit.json`。

## 当前调用是否正确

认证和基本聊天请求与文档一致：`POST /apis/auth` 读取 `data.access_token`，业务请求使用 Bearer Token；聊天请求传 `botId`、`content`、`isStream`。文档示例域名为 `lingxinai.com`，客户端使用 `www.ai-role.cn`，当前认证、列表、详情、历史均成功，不能仅因域名不同认定调用错误。此前部分智能体正常答题，证明基础文字聊天链路可用。

但客户端尚未完整遵循响应协议，现有试跑也没有实现题间上下文清理：

1. 文档 §3.3 提供 `POST /open/chat/clearContext`，请求为 `{"botId": ID, "courseProgressId": 0}`，成功返回 `role=flush_context` 标记。独立题目评测应在每题前清理，并检查成功状态；可以再通过 §3.2 的 `onlyLastSession=true` 查询清理后的最近上下文。当前评测脚本只调用 `send_message`，没有清理。历史显示每个已试跑智能体的多题消息位于同一 `chatId`。聊天记录共享会话本身不证明每条历史都送入模型，但志航连续问卷行为已说明业务状态不能假定独立。清理是否重置各上游工作流的全部状态仍需验证。
2. 文档 §3.1 明确部分 SSE 链路会二次 JSON 编码。客户端只解析一次，遇到字符串会在 `.get()` 出错后被宽泛异常捕获吞掉，返回空文本。离线按文档格式复现成立。
3. 文档 §7.1 示例用 `model=error` 判断 SSE 错误；§6 规定 JSON `success=false` / `code=901` 可能随 HTTP 200 返回。现有客户端将两类错误文本当作普通回复。离线模拟均复现。评测脚本目前只特判一个具体错误文案，不能替代统一业务错误处理。
4. 文档 §3.1 规定流式结束字段是 `finishReason`，且要处理 `conversationId`、`options`、`customMessage`、`nextBotId`、`metainfo` 等业务信息。现有客户端只拼接文字、等待流关闭，丢弃其他信息；对只需文字的普通聊天可以工作，对问卷、切换智能体和多媒体流程并不完整。

原30次请求结果应保留为协议/角色行为试跑记录，不能当作已隔离、严格可比的 ToMBench 分数。

## 对比实验需要的条件

先修复协议解析与错误识别，接入每题清理并验证工作流状态重置。然后由服务端提供同一模型/版本的基础调用与启用harness的调用，记录系统提示词、温度、记忆、工具、检索、工作流和后处理差异。若要区分角色提示词与编排本身的贡献，应保留“基础模型”“同模型加相同角色提示词”“同模型加角色提示词和流程编排”三组。当前接口没有公开关闭harness的参数，不应杜撰字段或把清理上下文等同于关闭harness。
